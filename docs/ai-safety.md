# AI safety and grounding

The existing guided interview order and deterministic normalizer remain the fallback, and the recommender remains authoritative. `backend/app/ai` provides a provider-neutral client, strict Pydantic output schemas, a bounded interview-turn interpreter, validated session tools and privacy-safe operational logs. AI is disabled by default. When configured, the regular `POST /api/v1/interview/session/{id}/message` flow requires consent, accepts text or browser/server voice transcripts, validates extracted fields, retains the raw answer and persists only allow-listed profile fields. The existing session profile remains canonical; `profile_evidence` links extracted values to their source answer. Common computer-skill variants are mapped to stable ids such as `basic_computer`, `basic_excel`, and `ms_office`. Low-confidence or conflicting candidates wait for beneficiary review. Model confidence is an uncertainty estimate, never factual certainty. Beneficiaries can confirm, correct, or remove each extracted field before confirming the profile. The AI cannot select arbitrary database operations or directly make eligibility/recommendation decisions. If the provider is unavailable or output fails validation, the same message is processed by the existing deterministic interview. The separate `ai-interpret` endpoint remains a non-persisting diagnostic suggestion route.

Configure `AI_PROVIDER=ollama` or `openai_compatible`, `AI_MODEL`, and `AI_BASE_URL`; `AI_API_KEY` is optional for local providers and must come from the deployment environment when needed. Also configure `AI_TEMPERATURE`, `AI_MAX_TOKENS`, and `AI_TIMEOUT_SECONDS`. For Ollama, use its OpenAI-compatible endpoint such as `http://localhost:11434/v1`. Do not expose provider keys to the frontend.

AI logs contain only request/session identifiers, operation/model, latency, outcome, validation status and token counts when supplied. Prompts, raw beneficiary answers, model outputs and hidden chain-of-thought are not logged. No chain-of-thought is requested or stored.

Recommendations come from rows seeded in the pathway catalogue. Seeded entries are demo pathway concepts, not official course names. The existing interest/skills/demand/feasibility/preference weights remain 30/25/20/15/10. A local curated-concept and character n-gram matcher compares interests to pathway text and skills to requirements; it only normalizes explicit skill equivalents and breaks ties after deterministic score and overlap. It does not add to or replace the deterministic score. Recommendation records persist that score, component scores, semantic values, matched/missing skills, demand and feasibility details, data sources, and model version. When configured, the LLM receives only a validated recommendation context and selects bounded explanation codes. The backend renders prose from the validated facts, so model output cannot introduce new course claims. Invalid or unavailable AI uses a grounded deterministic explanation. Seeded entries remain demo concepts; the system avoids asserting eligibility, fees, duration, openings, placement or scheme coverage. Unknown programme questions should be referred to the counsellor.

Speech recognition is optional. Whisper is loaded only if installed; missing model/runtime falls back to browser recognition or text. The Bhashini class is an adapter seam and does not make a network request until an endpoint-specific pipeline is configured. Text-to-speech uses browser synthesis.

There are no measured ASR accuracy, employment, placement, recommendation quality or fairness outcomes. Synthetic data must not be represented as pilot evidence.

RAG, unrestricted agents/tools and AI-generated recommendations are not implemented in this phase. Future retrieval must use reviewed sources and return citations; agent tools must be allow-listed, typed, and unable to execute arbitrary SQL or directly change beneficiary records.
